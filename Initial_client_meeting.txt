### 2. Clinical Coding Reference

*File: clinical_codes_reference.csv (reference codes)*

**This is a lookup/join table for the encounter data.** The patient encounters dataset uses numeric codes for several categorical fields. This reference file maps those codes to their human-readable descriptions (admission types, discharge dispositions, admission sources).

**You will need to join this reference table** to your encounter data to understand what these coded fields mean. Without this join, several columns are just meaningless integers. Pay close attention to discharge dispositions — some have important implications for your readmission model.

### 3. Patient Medication Feedback Database

*File: patient_medication_feedback.csv (~180,000 patient drug reviews)*

**Patient-Reported Drug Reviews:**

- Patient ID (separate from encounter data)
- Drug name, condition treated
- Review text (detailed patient narratives about their medication experience)
- Effectiveness rating and numeric rating
- Date of review

**For your NLP model:** Classify patient reviews into the correct effectiveness category using the `review_text` field. This is real patient language — informal, emotional, sometimes contradictory. Explore the effectiveness categories and consider whether simplification makes sense.

**Note:** This dataset covers medications across all conditions our patients are treated for, not just diabetes drugs. This reflects the reality that our diabetic patient population has complex comorbidities.

### 4. Diabetic Retinopathy Screening Images

*Directory: retinal_scan_images/ (retinal images)Labels: retinal_labels.csv (image labels)*

**Medical Imaging Dataset:**

- Fundus photography from diabetic patients
- PNG format
- Collected during routine diabetic eye exams
- Mix of normal and pathological cases
- Severity grades (0-4 scale) ranging from no retinopathy to proliferative retinopathy

**Important — Image/Label Mismatch:** The labels file contains more entries than there are actual image files on disk. You must match labels to existing images and filter accordingly. This is a common real-world data quality issue.

**Dataset Context:** This is a small medical imaging dataset with significant class imbalance across severity grades. Consider how to handle this for training. For clinical decision-making, think about what classification split is most useful for screening purposes.

## What We Need From You

### 5 Required AI Models

### Model 1: Readmission Risk — Traditional ML

- **Binary classification:** will this patient be readmitted (yes/no)?
- **Important:** The raw `readmitted` column has 3 values (`<30`, `>30`, `NO`). You must create a binary target: readmitted = 1 (both `<30` AND `>30`), not readmitted = 0 (`NO`). See `preprocessing_hints.py`.
- Use classical ML algorithms (XGBoost, Random Forest, Logistic Regression, etc.)
- Must be interpretable — clinicians need to understand WHY a patient is flagged
- **Minimum Benchmark:** AUC-ROC > 0.70
- **Stretch Goal:** AUC-ROC > 0.80
- **Required:** SHAP or feature importance analysis

### Model 2: Readmission Risk — Deep Neural Network

- Same binary readmission prediction task as Model 1, but using a deep learning approach
- Build a neural network (TensorFlow/Keras) on the tabular encounter data
- Compare performance against your traditional ML model
- **Minimum Benchmark:** AUC-ROC > 0.70
- **Stretch Goal:** AUC-ROC > 0.80
- **Required:** Show how DNN performance compares to traditional ML and explain the trade-offs

### Model 3: Diabetic Retinopathy Detection — CNN

- **Binary classification:** Does this patient have diabetic retinopathy (DR vs. No DR)?
- **Important:** The raw labels have 5 severity grades. You must convert to binary: No DR vs. Has DR. See `preprocessing_hints.py`.
- Build or fine-tune a convolutional neural network
- **Minimum Benchmark:** Overall accuracy > 70%, Sensitivity for DR detection > 80%
- **Stretch Goal:** Accuracy > 85%, Sensitivity > 85%
- **Also valued:** Grad-CAM or other interpretability visualizations

### Model 4: Patient Drug Review Classification — NLP

- **Classify patient drug reviews into 3 effectiveness categories:** "Highly Effective", "Somewhat Effective", and "Ineffective". See `preprocessing_hints.py` for the mapping from the raw 5-class data.
- Use NLP techniques (TF-IDF + classifier, word embeddings, or transformers)
- Handle messy, real-world patient text (typos, slang, medical jargon, emotional language)
- **Minimum Benchmark:** Accuracy > 70%, weighted F1 > 0.65
- **Stretch Goal:** Accuracy > 82%, weighted F1 > 0.78
- **Also valued:** Key phrase extraction, side effect pattern identification

### Model 5: Clinical Innovation — Your Choice

- Identify a clinical problem in the data that we haven't asked you to solve
- Build a model that addresses a genuine clinical need
- **You must use the data we've provided** — do not bring in external datasets. The goal is to show us what's possible with what we already have.
- Ideas to explore: ICU transfer prediction, length of stay optimization, diabetes subtype clustering, medication interaction risk scoring
- Think creatively about how to leverage our data in ways we haven't considered — could you use agents, RAG, or other innovative techniques to extract more value?
- **Must include:** Clear clinical justification, defined success metric, ROI estimate
- **We want you to surprise us.** The winning team won't just build what we asked for — they'll identify problems we didn't know we could solve.

**Critical — How Testing Works:**

Your models will be tested on **completely unseen data** that I hold back. This test data looks exactly like the raw data you downloaded — same columns, same formats, same messiness (e.g., `?` values, `[70-80)` age brackets, missing fields). Your `predict.py` must:

1. **Accept raw data** in the same format as what you downloaded (not pre-cleaned data)
2. **Apply all preprocessing automatically** — the same cleaning, encoding, and feature engineering you did during training must happen inside your prediction pipeline
3. **Output predictions** in the exact format specified by the output templates

Think of it this way: I will drop a fresh CSV (or images) into your `test_data/` folder and run `python bulk_test.py --all`. Your code needs to handle everything from raw input to final predictions **without any manual steps**. If your pipeline only works on data you've already cleaned by hand, it will break.

Build your preprocessing as reusable functions in `pipelines/data_pipeline.py` and import them in both your `train.py` and `predict.py`. This is how real production ML works — the same pipeline handles training data and new data.

## Data Quality & Integration Notes

**Real-World Data Challenges:**

- Missing values are encoded in ways you may not expect — investigate how nulls are represented
- Some patients in the encounter data cannot physically be readmitted — think about which discharge dispositions make readmission impossible and exclude them. Use the clinical codes reference table.
- Retinal image labels are in a separate file that must be matched to actual images on disk
- Age is stored in a non-numeric format
- ICD-9 diagnostic codes are worth exploring for feature engineering
- Medication review text contains typos, abbreviations, and inconsistent formatting

**This messiness is intentional** — real healthcare data is never perfect. Your ability to handle these challenges is part of the evaluation.

**A Note on Patient Cohorts:** The medication feedback data comes from a different patient system than the encounter data. The patient IDs do NOT match between these datasets. Plan your models accordingly — don't try to join them.

## Common Pitfalls (Learn from Previous Teams)

**Teams have failed because they:**

- Didn't standardize their output format (columns didn't match, evaluation script failed)
- Left final code in notebooks instead of `.py` files
- Built models with high accuracy but poor interpretability
- Ignored class imbalance and reported misleading metrics
- Let one team member do all the work (peer evals caught this)
- Didn't test their bulk_test scripts before submission

**Teams have succeeded because they:**

- Followed the repo template exactly
- Tested their output format against the templates early
- Built modular, clean pipelines
- Compared models thoughtfully (not just "DNN is better")
- Told a compelling clinical story in their presentation
- Showed genuine understanding of healthcare workflows
